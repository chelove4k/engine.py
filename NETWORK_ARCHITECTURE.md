# Архитектура мультиплеера (Server Authority Model)

Документ описывает, как в существующий движок `pyengine/engine.py` добавляется
сетевой режим. Ничего из текущего поведения не ломается: игра без сети
работает ровно как сегодня.

Реализация — **только стандартная библиотека Python** (`socket`, `selectors`,
`struct`, `threading`, `multiprocessing`, `queue`, `json`, `zlib`, `time`).
Сторонние сетевые библиотеки (ENet, Twisted, asyncio-фреймворки) не
используются.

---

## 1. Что уже есть в движке и почему это удобно

| Механизм движка | Как используется в сети |
| --- | --- |
| Фиксированный тик 100 Гц, `tick` и `time` в `engine_state` | Сетевой тик = тик симуляции. Сервер — мастер часов, клиент подстраивается |
| `scripter_runner` — кооперативный цикл скриптов, один проход = один снимок состояния | Тот же цикл крутится и на сервере, без окна Arcade |
| `VisualCache` — общая память, запись `(x, y, tick, rotation, scale, alpha, layer)` | Готовый источник данных для снапшотов и готовый приёмник коррекций |
| Интерполяция в `render.Game` по `tick` | Переиспользуется как есть, только задержка в сети больше |
| Ввод скриптов через shared memory (`keyboard_ring`, `motion_cache`, `input_cache`) | Единственная точка подмены: локальное устройство → сетевой канал игрока |
| `scripting.network: list[str]` (уже есть в сцене и в `GameObject.Scripting`) | Становится декларацией сетевой роли объекта |
| `GameObject`/`Component` API, `fixed_update` | Не меняется: скрипты пишутся как раньше и работают на сервере и на клиенте |

Ключевая идея: **сервер — это тот же движок, но без рендера, с вводом из сети
и часами, которые он же и задаёт.** Клиент — тот же движок с рендером, который
дополнительно предсказывает своего игрока и принимает коррекции.

---

## 2. Ключевые решения

| Вопрос | Решение | Причина |
| --- | --- | --- |
| Транспорт | TCP, кадры с префиксом длины, неблокирующие сокеты + `selectors` | Надёжность и порядок «из коробки», работает на Windows без настройки; при 20 Гц снапшотах пропускной способности хватает |
| Роль сервера | Отдельный headless-процесс: `Stream` + `scripter_runner` без Arcade | Сервер не зависит от FPS и окна; код симуляции один и тот же |
| Источник истины | Серверный тик и серверное состояние | Требование Server Authority |
| Что шлёт клиент | Только **ввод** + «заявку» на проверку своего предсказания | Клиент не может диктовать позиции |
| Проверка клиента | Сервер сам считает тот же тик и сравнивает состояние с заявкой клиента | «Сервер подтверждает, что расчёты клиента правильные» |
| Расхождение | `CORRECTION`: сервер присылает истинное состояние, клиент плавно его принимает | Без телепортов и «резинки» |
| Предсказание | Только объекты своего игрока (`owner`) | Минимальная сложность, максимальный эффект |
| Остальные игроки | Интерполяция между снапшотами, без предсказания | Стандартная схема, дёшево |
| Снапшоты | 20 Гц, дельта от подтверждённого снапшота | Трафик ~ в 5 раз ниже, чем 100 Гц полными снапшотами |
| Эффективность | Бинарный `struct` на горячем пути, дельта-снапшоты и AOI с первого сетевого этапа | Не переписывать протокол и сборку снапшотов позже |
| Совместимость | `scripting.network: []` (или отсутствие) = объект живёт как в одиночной игре | Ноль регрессий |

## 3. Топология процессов

### Сервер (`server_main.py`)

```
┌──────────────────────────── server host ─────────────────────────────┐
│                                                                       │
│  GameServer (главный процесс)                                         │
│   ├── accept-loop (selectors, неблокирующие сокеты)                   │
│   ├── поток чтения: кадр → разбор → InputQueue игрока                  │
│   ├── поток снапшотов: VisualCache → дельта-кодек → send-буферы       │
│   └── InputQueue + NetClock                                          │
│              │ команды через multiprocessing.Queue                    │
│              ▼                                                        │
│  Stream (процесс, как сейчас)  ── worker_queues ──►  scripter_runner  │
│   ├── реестр объектов                                (100 Гц, скрипты) │
│   ├── применение ввода к каналам игроков                              │
│   ├── публикация tick/time в engine_state                             │
│   └── VisualCache / IdCache (shared memory)                           │
└───────────────────────────────────────────────────────────────────────┘
```

Сервер не создаёт окно. `Stream` в серверном режиме сам публикует `tick`
(сейчас это делает `tact_counter` в процессе рендера), поэтому тик и
применение ввода происходят в одном проходе — это важно для детерминизма.

### Клиент (`client_main.py` / `python render.py --mode join|host`)

```
┌──────────────────────────── клиент ───────────────────────────────────┐
│  Game (render, Arcade)                                                │
│   ├── интерполяция удалённых объектов по SnapshotCache                │
│   ├── затухающие визуальные смещения из CorrectionBuffer              │
│   ├── локальный ввод → и в скрипты, и в NetClient                     │
│   └── NetClient.pump() в on_update (неблокирующий сокет)              │
│                                                                       │
│  Stream ── scripter_runner (100 Гц, те же скрипты, предсказание)      │
│                                                                       │
│  NetClient (в том же процессе, что и рендер)                          │
│   ├── сокет, handshake, ping/clock sync                               │
│   ├── INPUT-пакеты с заявкой на проверку                              │
│   └── SNAPSHOT/CORRECTION → SnapshotState / CorrectionBuffer          │
└───────────────────────────────────────────────────────────────────────┘
```

`NetClient` живёт в процессе рендера, а не отдельным процессом: сокет
неблокирующий, `pump()` вызывается из `Game.on_update` и успевает разобрать
входящие кадры между отрисовками. Отдельный процесс только добавил бы
межпроцессную передачу ввода и снапшотов на каждом тике.

### Режим `host`

`python render.py --mode host` (или `server_main.py` для чистого сервера):

1. Клиент запускает `server_main.py` подпроцессом (`--no-console`);
2. ждёт, пока headless-сервер зарегистрирует сцену и откроет порт;
3. подключается к `127.0.0.1` обычным `NetClient` и играет;
4. при выходе останавливает дочерний сервер.

Сервер и клиент — разные процессы, поэтому падение окна не роняет мир, а
сервер можно оставить запущенным для других игроков.

## 4. Протокол

### 4.1. Кадр

```
uint32 length (big-endian, длина payload)
payload = header (10 байт) + body
header  = struct '!BBII' : msg_type u8, flags u8, seq u32, tick u32
```

* Заголовок — 10 байт. `seq` — сквозной номер кадра (для `ACK` это
  подтверждаемый серверный тик, для `INPUT` — номер кадра ввода клиента).
* `flags`: `MORE` (фрагментация снапшота), `RELIABLE` (зарезервировано),
  `RESET` (полный снапшот вместо дельты).
* Максимальный кадр — 64 КиБ. Превышение → разрыв соединения.
* Тело: `struct` для горячих полей + `json` (UTF-8) для переменных.
  `pickle` и `eval` на сетевых данных запрещены.

### 4.2. Сообщения

| Направление | Тип | Поля |
| --- | --- | --- |
| C→S | `HELLO` | protocol u16, scene_hash u32, scripts_hash u32, name str, token str |
| S→C | `WELCOME` | client_id u16, tick_rate u16, snapshot_hz u8, input_delay u8, max_players u16, world_seed u32, owner_render_id u32 |
| S→C | `REJECT` | code u16, text str |
| C→S | `INPUT` | client_tick u32, seq u32, keys bitset(32 Б), mouse_x/y f32, buttons u8, clicks[(render_id u32, button u8)], claims[(render_id u32, x f32, y f32, rot f32, state_crc u32)] |
| S→C | `SNAPSHOT` | tick u32, base_tick u32, ack_seq u32, spawns[], despawns[], records[] |
| S→C | `CORRECTION` | tick u32, render_id u32, x/y/rot/scale/alpha f32, last_ack_seq u32, reason u8 |
| S→C | `EVENT` | name str, payload json (звук, UI, эффекты, вызовы скриптов) |
| C→S | `RESYNC` | last_tick u32 (клиент потерял базу дельты) |
| оба | `PING` / `PONG` | t0, t1, t2, t3 u64 (микросекунды, для offset/RTT) |

`SNAPSHOT.records[]`: `render_id u32`, `mask u8` (какие поля изменились),
дальше только изменённые `f32` из набора `x, y, rotation, scale, alpha, layer`.
Спрайт передаётся один раз при спавне и при смене (отдельный флаг).

### 4.3. Ограничения

* Ключи — только из таблицы `net/keys.py` (построена из нормализованных имён
  движка). Неизвестный ключ отбрасывается.
* Мышь: `x/y` клампятся в границы мира/вьюпорта клиента, `buttons` — 3 бита
  (левая = 1, средняя = 2, правая = 4).
* `INPUT` не чаще одного раза за тик, не более 4 кадров «вперёд» от серверного
  тика; лишние отбрасываются.
* Таблица `clicks` — не более 8 записей за кадр.

## 5. Тик, часы, доставка ввода

1. Часы сервера (`ServerClock` в `GameServer`) идут по `time.perf_counter()`
   и определяют целевой тик с учётом `INPUT_DELAY_TICKS`.
2. `GameServer` на каждый тик отправляет `net_tick` в рабочий процесс
   (`EngineWorld`). `scripter_runner` в серверном режиме делает **ровно один
   шаг симуляции на тик**, публикует `tick/time` в `engine_state` и
   подтверждает выполнение через `executed_tick`. `GameServer` ждёт это
   подтверждение, прежде чем проверять заявки и снимать снапшот.
3. Перед проходом скриптов применяется ввод на тик `T`:
   `InputQueue.take(T)` для каждого игрока.
4. Кадры ввода упорядочены по `seq`; сервер потребляет не более одного
   нового кадра за тик. Привязка к абсолютному `client_tick` не используется:
   часы клиента и сервера расходятся, а `seq` устойчив к задержке и джиттеру.
   Очередь на игрока — до 16 тиков; `INPUT_DELAY_TICKS` задаёт, насколько
   сервер отстаёт от часов, чтобы кадр успел дойти.
5. Если ввод на тик отсутствует — повторяется последний кадр не более 5 тиков,
   затем «все клавиши отпущены». Это исключает остановку мира из-за одного
   потерянного пакета.
6. Клиент синхронизирует часы по `PING/PONG`:
   `offset = ((t1 - t0) + (t2 - t3)) / 2`, сглаживание по медиане последних 8
   измерений; локальный период подстраивается в пределах ±1 %, назад тик не
   идёт никогда.
7. Рендер удалённых объектов: `render_tick = server_tick_estimate -
   INTERP_DELAY_TICKS` (по умолчанию 10 тиков = 100 мс), интерполяция уже
   реализована в `render.Game`.

## 6. Предсказание и коррекция (клиент)

Термины:
* **owner-объект** — объект с `"network": ["owner"]`, закреплённый за игроком.
* **predicted state** — состояние, которое клиент получил, прокрутив свои
  скрипты с локальным вводом.
* **authoritative state** — состояние того же тика на сервере.

Цикл:

```
кадр N (клиент)
  локальный ввод → скрипты → VisualCache → экран (0 задержки)
  INPUT(seq=N, claimed=VisualCache[owner] до применения кадра) ──► сервер

тик сервера (со сдвигом input_delay)
  взять следующий кадр игрока (по seq)
  применить ввод к его каналам
  прогнать те же скрипты
  сравнить своё состояние ПОСЛЕ первого применения кадра N-1 с claimed(N)
  snapshot { состояние мира, ack_seq }

клиент получает snapshot
  удалённые объекты: интерполяция к снапшоту
  owner: |claimed - авторитет| <= EPS  → тихо
         иначе CORRECTION → CorrectionBuffer (только рендер)
```

* `CorrectionBuffer` хранит `dx, dy, drot, start_time` на `render_id`.
  `render.Game` прибавляет смещение к позиции отрисовки и линейно гасит его за
  `CORRECTION_DECAY = 0.15 с`. Симуляция и скрипты смещения не видят.
* Большая ошибка (`> 64` единиц или флаг телепорта) применяется мгновенно,
  без затухания.
* История предсказаний клиента (`PredictionHistory`) хранит кольцо
  `tick → (x, y, rot, seq)` для owner-объектов; сверка идёт по `seq`, а не по
  абсолютному тику, поэтому расхождение часов ей не мешает.

**Честное ограничение:** rollback-replay произвольных Python-скриптов не
делается — скрипты могут хранить произвольное состояние, а повтор ввода стоил
бы дорого. Выбран простой и быстрый путь: клиент принимает истинное состояние,
продолжает симуляцию с него, а рендер гасит разницу. Предсказание при этом
работает без задержки, а коррекции остаются редкими при стабильной сети.

## 7. Серверная проверка расчётов клиента

Это ядро требования «сервер подтверждает правильность расчётов клиента».

1. Клиент **не присылает** позиции как истину. Он присылает `claims` —
   заявку: «перед применением кадра `seq` мой объект был в (x, y, rot),
   crc = …».
2. Сервер применяет кадры строго по `seq` и запоминает авторитетное состояние
   **до** каждого нового кадра. Сравниваются приращения:
   `claim_N - claim_{N-1}` против `server_before_N - server_before_{N-1}`.
   * сверка идёт по `seq`, а не по абсолютному тику: часы клиента и сервера
     могут расходиться;
   * повторы последнего кадра при нехватке ввода (`INPUT_REPEAT_TICKS`) и
     опоздавшие кадры (`seq` уже потреблён) в сверке не участвуют;
   * джиттер может задержать кадр на 1–3 тика, и сервер законно повторит
     ввод. Поэтому допуск на приращение растёт вместе с движением сервера за
     этот интервал (`CLAIM_DELTA_TOLERANCE` — нижняя граница), а не является
     жёсткой константой;
   * накопленный абсолютный сдвиг ограничен `MAX_CLAIM_DRIFT` (32 единицы):
     так ловится телепорт/подмена позиции, даже если приращение совпало.
3. Сравнение:
   * ошибка приращения и поворота в допуске, дрейф в норме → расчёт
     подтверждён, ничего не отправляется;
   * иначе → `CORRECTION` с истинным состоянием, инкремент `desync_count`.
     Визуальная поправка гасится `CorrectionBuffer`, симуляция не
     перематывается.
4. `desync_count` на игрока за окно 10 с:
   * `> 5` — предупреждение в лог сервера;
   * `> 25` или одиночная ошибка `> 500` единиц — `KICK`, но только если
     античит переключён в режим `kick`.
   По умолчанию режим `log`: сервер считает и пишет расхождения, но не
   отключает игрока. Переключение на лету из терминала сервера:
   `anticheat log` / `anticheat kick`.
5. Дополнительные проверки ввода (не зависят от скриптов):
   * скорость: `|Δposition| за тик > MAX_SPEED * dt` → коррекция + violation;
   * телепорт без `EVENT` от серверного скрипта → violation;
   * клиент не может создавать/удалять объекты, менять `scripting.network`,
     вызывать серверные скрипты.
6. Хэши при подключении: `scene_hash` + `scripts_hash`. Несовпадение →
   `REJECT` (нельзя играть с изменёнными скриптами).
7. Сервер логирует по каждому игроку: RTT, потери (для TCP — ретрансмиты по
   таймауту), `desync_count`, среднюю ошибку предсказания, тик-лаг.

## 8. `scripting.network`: роли объектов

Сейчас поле — `list[str]` и проверяется в `scene.py`. Семантика расширяется,
неизвестные значения игнорируются с предупреждением.

| Значение | Смысл |
| --- | --- |
| `[]` / отсутствует | Локальный объект. Одиночная игра и клиентские эффекты. На сервер не реплицируется |
| `"replicate"` | Состояние реплицируется всем клиентам, симуляция только на сервере |
| `"owner"` | Объект игрока: сервер авторитетен, владелец предсказывает локально |
| `"input"` | Объект читает ввод назначенного игрока (камера, контроллеры, UI) |
| `"server"` | Существует только на сервере (спавнеры, AI, логика матча) |
| `"predict"` | Клиентские эффекты (анимация, UI) выполняются и локально, и на сервере |
| `"room:<name>"` | Фильтр интереса (этап M4) |

Назначение владельца:

* при `HELLO` сервер выдаёт `player_id` и `render_id` его объектов;
* если в сцене есть объекты с `"owner"` без привязки — сервер выдаёт их
  по порядку подключения;
* скрипт-менеджер может спавнить объекты на игрока через
  `self.Net.spawn_for(player_id, json)`.

API скриптов (доступно и на клиенте, и на сервере):

```python
self.Net.is_server          # bool
self.Net.player_id          # int | None
self.Net.player_count       # int
self.Net.is_owner(obj)      # bool
self.Net.send_event(name, payload)   # сервер → клиенты (звук, UI)
```

## 9. Ввод: `InputSource`

Единственная точка подмены локального ввода на сетевой.

```python
class InputSnapshot:              # net/input_source.py — неизменяемый снимок
    tick, seq, pressed, pressed_down, pressed_up,
    mouse_x, mouse_y, buttons, buttons_down, buttons_up, clicks, claims

class FrameInputSource:           # сервер: очередь кадров одного игрока
    current: InputSnapshot
    def advance(tick): ...        # ровно один раз за тик
```

* `script.step` уже получает `state` с `tick`. Перед каждым `fixed_update`
  он берёт `input_source.snapshot_for_tick(_simulation_tick)` — ввод становится
  **потиковым**, а не «последний на проход». Это нужно и для предсказания, и
  для сверки.
* Объект без сетевых директив получает `LocalInput` — поведение не меняется.
* `Keyboard`/`Mouse` остаются прежним API для скриптов, меняется только
  источник данных внутри.

## 10. Файловая структура

```
engine.py/
  net/
    __init__.py
    config.py          # NET_* константы и таймауты
    protocol.py        # типы сообщений, struct-кодеки, CRC, версия протокола
    keys.py            # таблица клавиш → биты, нормализация
    transport.py       # TcpListener/TcpConnection: framing, неблокирующий I/O
    server.py          # GameServer, ClientSession, приём/отправка, rate limit
    client.py          # NetClient: handshake, ping, INPUT, приём снапшотов
    state.py           # SnapshotState: сборка/применение дельт
    input_queue.py     # очередь ввода на игрока, повтор последнего кадра
    clock.py           # NetClock (сервер), ClockSync (клиент)
    reconcile.py       # PredictionHistory, сверка заявок, CorrectionBuffer
    input_source.py    # InputSource / FrameInputSource / InputSnapshot
    simulation.py      # ServerSimulation: источники ввода по игрокам
    engine_world.py    # мост GameServer ↔ рабочий процесс симуляции
    directives.py      # разбор scripting.network
    hashes.py          # scene_hash / scripts_hash для HELLO
    loopback.py        # транспорт в памяти для тестов
  server_main.py       # python server_main.py --port 7777 --scene arena.json
  client_main.py       # python client_main.py --host 127.0.0.1 --port 7777
  stream.py            # + net-команды, тик сервера, сбор снапшотов
  scripter_runner.py   # + input_source, строгий режим «один тик на проход»
  pyengine.py          # + Net-фасад, потиковый ввод, директивы network
  render.py            # + режим join: SnapshotCache, CorrectionCache, offsets
  config.py            # без изменений (сетевые константы — в net/config.py)
```

## 11. Изменения в существующих файлах (точечно)

**`pyengine.py`**
* `script.step`: обновление `__pressed_keys`/mouse из `input_source` на каждый
  `fixed_update` (по `_simulation_tick`).
* `script.__init__`: принимает `input_source`, `net`;
  `self.Net` — фасад.
* `__Scripting`: разбор директив `network` в структурированный вид
  (`replicate`, `owner`, `input`, `server`, `predict`, `rooms`).
* `Keyboard`/`Mouse`: чтение через `InputSource`, публичный API не меняется.

**`stream.py`**
* Новые команды очереди: `net_input` (пакет ввода игрока), `net_join`,
  `net_leave`, `net_correction`, `net_event`, `net_stats`.
* Серверный режим: публикация `tick/time` внутри `Stream`, вызов
  `input_queue.apply_for_tick(...)` перед проходом воркера.
* `add_script`: прокидывает `input_source` по директивам объекта.
* Клиентский режим: применение `CORRECTION` к `VisualCache` + запись в
  `CorrectionCache`.

**`scripter_runner.py`**
* Передача `input_source` в конструктор скрипта.
* Флаг `strict_tick=True` для сервера: один тик на проход.

**`render.py`**
* `Game.__init__` дополнительно принимает `net_client`, `net_owner_render_id`.
* При отрисовке: `position = interp(snapshot) + decay(correction)` для
  owner-объекта; удалённые объекты берут позицию только из снапшотов.
* `main()` получает `--mode solo|join|host`; в `join` поднимает `NetClient`,
  в `host` дополнительно запускает `server_main.py` подпроцессом.
* `NetClient.pump()` вызывается из `on_update`; ввод уходит с заявкой
  (`claim`) на проверку. Кадр отправляется не чаще одного раза на тик
  локальной симуляции: дубли одного тика дали бы пару «0 движения» против
  одного серверного тика и ложный desync.

**`scene.py`**
* Валидация директив `network` (предупреждение вместо падения), проверка
  `deterministic` (bool).

## 13. Безопасность и устойчивость

* Никакого `pickle`, `eval`, `exec` для сетевых данных; только `struct` и
  `json` с лимитами длины/глубины.
* Лимит кадра, лимит очередей, таймауты чтения, лимит подключений с одного IP.
* Валидация каждого поля: типы, диапазоны, `NaN/Inf` отбрасываются.
* Снапшоты не копятся: если клиент не успевает — старый снапшот вытесняется,
  а не раздувает память.
* Сервер не доверяет `render_id` из клиентских `claims`: проверяется, что
  объект существует, принадлежит этому игроку и имеет `owner`.
* `HELLO` с неверным `scene_hash`/`scripts_hash` → `REJECT`.
* Опционально (по флагу): `ssl` из стандартной библиотеки поверх сокета.
  По умолчанию выключено, чтобы не усложнять локальную отладку.

## 14. Производительность (бюджеты)

* Ввод: 100 Гц × ~48 Б × 8 игроков ≈ 38 КБ/с на сервер — несущественно.
* Снапшот: 20 Гц × 64 объекта × ~24 Б (дельта) ≈ 30 КБ/с на клиента.
* Сервер: разбор ввода и сборка снапшотов — отдельные потоки, симуляция не
  блокируется сокетами (`send` только в буфер, при переполнении — вытеснение).
* Цель этапа M4: N игроков (по `--max-players`) × 100 объектов в AOI, CPU
  сервера < 50 % одного ядра, RTT-независимая стабильность при 100 ± 40 мс.

## 15. Этапы внедрения

| Этап | Результат | Проверка |
| --- | --- | --- |
| **M0. Каркас** | `net/` с протоколом, транспортом, loopback; юнит-тесты | Тесты кодеков и framing, без изменения игры |
| **M1. Сервер и вход** | headless-сервер, `WELCOME`, дельта-снапшоты 20 Гц, базовая зона интереса, удалённые объекты видны | Два клиента видят друг друга, движение по вводу |
| **M2. Предсказание** | owner-объекты предсказываются, коррекции с затуханием, потиковый ввод | Субъективно «0 задержки», нет резинки |
| **M3. Валидация** | `claims` + CRC, `CORRECTION`, счётчики нарушений, лог античита | Тест «клиент врёт» → коррекция и violation |
| **M4. Нагрузка и отладка** | метрики, консоль `netstat`, профилирование, тюнинг буферов; проверка на N игроков | N игроков (по `--max-players`), 100 объектов, стабильный тик |

Каждый этап заканчивается рабочим состоянием: после M1 уже можно играть
вдвоём, дальше — только качество.

## 16. Тестирование

* **Кодеки**: round-trip всех сообщений, обрезка/склейка кадров, мусорные
  длины, `NaN`, превышение лимитов.
* **Детерминизм**: одна сцена + один набор вводов, два прогона → одинаковый
  CRC состояния на каждом тике.
* **Очередь ввода**: перестановка, дубликаты, опоздания, пропуски → мир не
  останавливается.
* **Реконсиляция**: искусственная ошибка 3 единицы → поправка гаснет за
  ≤ 0.2 с, суммарное смещение → 0.
* **Интеграция**: 2 клиента через `loopback` с задержкой 100 ± 30 мс и
  потерей 2 % → расхождение < допуска, число коррекций в норме.
* **Античит**: клиент присылает завышенную позицию → `CORRECTION` +
  `desync_count++`; клиент шлёт чужой `render_id` → отброс.
* **Нагрузка**: `tests/stress_net.py` — N ботов (по `--max-players`), 5 минут,
  отчёт по тикам, RTT и трафику.

---

## 17. Что не входит в объём

* NAT punch-through, matchmaking, лобби-сервис, список серверов.
* Голосовой чат, шифрование по умолчанию.
* UDP-транспорт (архитектура готова: `transport.py` — единственная точка).
* Rollback-replay состояния скриптов: выбран простой и быстрый путь без него.
* Физический движок и серверная физика: коллизии остаются в скриптах, как
  сейчас.

## 18. Зафиксированные решения

1. **Эффективность сразу**: бинарный `struct` на горячем пути, дельта-снапшоты,
   зона интереса и переиспользование буферов — без «сначала JSON, потом
   перепишем».
2. **Режим `host`**: сервер и локальный игрок в одном запуске. Плюс отдельные
   `server_main.py` и `client_main.py`.
3. **Число игроков** задаёт разработчик: `--max-players N` (по умолчанию 32),
   архитектура не имеет жёсткого потолка.
4. **Античит**: по умолчанию `log`. Переключение на лету из терминала:
   `anticheat log` и `anticheat kick`.
5. **Без replay**: предсказание + плавные коррекции, без отката состояния
   скриптов. Это проще и быстрее.
6. **Отладочная консоль**: запуск скриптов командой, статистика, управление
   античитом и кик — см. раздел 19.

## 19. Отладочная консоль сервера

Консоль работает в процессе `GameServer` и не блокирует сетевой цикл.
Команды вводятся в терминал сервера (в режиме `host` — во второе окно
терминала или через оверлей).

| Команда | Действие |
| --- | --- |
| `script <path> [json]` | Создаёт `manager`-объект с указанным скриптом и регистрирует его через `Stream`. `json` — необязательные свойства компонента |
| `scripts` | Список запущенных отладочных скриптов с их `object_id` |
| `script_stop <object_id>` | Удаляет отладочный менеджер и останавливает скрипт |
| `players` | Список игроков: id, имя, RTT, desync, тик последнего ввода |
| `kick <client_id> [reason]` | Отключает игрока |
| `anticheat` | Показывает текущий режим и счётчики |
| `anticheat log` / `anticheat kick` | Переключает режим без перезапуска |
| `netstat` | Тик, снапшоты/с, трафик на игрока, размер очередей, дропы |
| `resync <client_id>` | Принудительно отправляет полный снапшот |
| `stop` | Штатное завершение сервера |

`script` создаёт объект так же, как это делает сцена:

```json
{
  "object_type": "manager",
  "id": {"name": "debug_1", "class": "debug_1", "type": "manager"},
  "scripting": {"scripts": ["access/scripts/debug_1.py"], "network": ["server"]}
}
```

Это позволяет проверять сетевые сценарии без правки сцены и перезапуска
сервера, а `script_stop` — убирать за собой.
