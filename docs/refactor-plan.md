# План упрощения и оптимизации движка

Документ фиксирует последовательность этапов. После каждого этапа движок
должен оставаться рабочим, а тесты — зелёными.

## Целевая архитектура

```text
Renderer-процесс (Arcade/OpenGL, один поток)
  ├─ ввод → shared memory
  ├─ отрисовка из visual shared memory
  └─ команды → очередь

Sim-процесс (один поток, кооперативный планировщик)
  ├─ World: реестр объектов, компоненты, скрипты
  ├─ фиксированный tick 100 Гц
  ├─ скрипты: update / fixed_update / события, с бюджетом времени
  └─ публикация visual state + tick + alpha + heartbeat
```

Один владелец на объект. Обмен через shared memory и очереди. `Manager` не
участвует в горячем пути.

## Этапы

| № | Этап | Основной результат |
|---|---|---|
| 0 | Baseline и страховка | Метрики «до», тег `pre-refactor` |
| 1 | Удаление мёртвого и дублей | Меньше кода и дублирующихся определений |
| 2 | Lifecycle и ID | Free-list слотов, generation, защита от stale-скриптов |
| 3 | Один sim-процесс | Вместо worker pool + thread-per-script — один поток и планировщик |
| 4 | Отказ от Manager | Регистрация и команды без прокси-объектов |
| 5 | Tick и интерполяция | Фиксированный шаг, публикация tick/alpha/heartbeat |
| 6 | Упрощение кэшей | Версии вместо сложных dirty-масок и stripe-локов |
| 7 | Оптимизация рендерера | O(1)-удаления, инкрементальный hit-grid, кэш текстур |
| 8 | API и структура | Понятный публичный контракт, документация, модули |
| 9 | Тесты и CI | Публичные тесты, детерминизм, стресс и shutdown |
| 10 | Spike по free-threading | Ответ по GIL с цифрами, без внедрения по умолчанию |

## Критерии готовности этапов 0–2

- baseline зафиксирован в `docs/baseline.md`;
- дубли `VisualCache`/`IdCache` сведены в `caches.py`;
- комментарии и докстринги переведены на русский;
- 100 000 циклов create/remove не увеличивают число занятых слотов;
- stale-команды `remove`/`render` от старого поколения не применяются к
  переиспользованному `render_id`;
- юнит-тесты и стресс-тесты проходят.

## Этап 2: lifecycle и ID

Что изменено:

- `Stream` выдаёт `render_id` из free-list `deque` и хранит поколение каждого
  слота в `_render_generations`;
- ответ регистрации содержит `object_id`, `render_id` и `generation`;
- `GameObject` хранит `_generation`, передаёт его в `remove`/`render` и
  публикует в `script_data`/`component_data`;
- повторный `register()` идемпотентен только для живого поколения; после
  удаления объект регистрируется заново;
- `Stream.__remove` освобождает слот только после удаления записи, а
  `__render`/`__remove` игнорируют команды чужого поколения;
- `find_object` переносит `_generation` в найденный объект;
- `validate_object_data` запрещает пользовательские `_id`, `object_id`,
  `render_id`, `_object_id`, `_render_id`, `_generation`.

Остаточная гонка: скрипт, который уже находится внутри `update()` в момент
удаления объекта, теоретически может успеть записать в общий visual cache до
следующей проверки живости. Этап 3 закрывает её: удаление и обновления
скриптов выполняются в одном потоке кооперативного планировщика.

## Позиция по GIL

- GIL нельзя отключить в обычной сборке CPython; нужна free-threaded сборка
  `python3.14t` (PEP 703, PEP 779).
- Free-threading даёт примерно 5–10% просадки single-thread и требует
  потокобезопасности всех общих структур.
- OpenGL-контекст всё равно должен работать в одном потоке.
- Основной выигрыш даёт не free-threading, а один sim-поток с кооперативным
  планировщиком и, при необходимости, шардирование по объектам на процессы.
- Free-threaded spike выполняется только после этапов 1–9 и только если
  профиль показывает CPU-bound нагрузку в скриптах.
