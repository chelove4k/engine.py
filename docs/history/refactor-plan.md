# План упрощения и оптимизации движка

> **Архив.** Исторический план рефакторинга. Пути к отчётам обновлены под
> текущую структуру `docs/reports/`; сам документ оставлен как есть.

Документ фиксирует последовательность этапов. После каждого этапа движок
должен оставаться рабочим, а тесты — зелёными.

## Целевая архитектура

```text
Renderer-процесс (Arcade/OpenGL, один поток)
  ├─ ввод → shared memory
  ├─ отрисовка из visual shared memory
  └─ команды → очередь

Sim-процесс (один поток, кооперативный планировщик)
  ├─ World: реестр объектов, компоненты, скрипты
  ├─ фиксированный tick 100 Гц
  ├─ скрипты: update / fixed_update / события, с бюджетом времени
  └─ публикация visual state + tick + alpha + heartbeat
```

Один владелец на объект. Обмен через shared memory и очереди. `Manager` не
участвует в горячем пути.

## Этапы

| № | Этап | Основной результат |
|---|---|---|
| 0 | Baseline и страховка | Метрики «до», тег `pre-refactor` |
| 1 | Удаление мёртвого и дублей | Меньше кода и дублирующихся определений |
| 2 | Lifecycle и ID | Free-list слотов, generation, защита от stale-скриптов |
| 3 | Один sim-процесс | Вместо worker pool + thread-per-script — один поток и планировщик |
| 4 | Отказ от Manager | Регистрация и команды без прокси-объектов |
| 5 | Планировщик и горячий путь | Снимок состояния на проход, `FieldView`, дедлайн-планирование |
| 6 | Упрощение кэшей | Версии вместо сложных dirty-масок и stripe-локов |
| 7 | Оптимизация рендерера | O(1)-удаления, инкрементальный hit-grid, кэш текстур |
| 8 | API и структура | Понятный публичный контракт, документация, модули |
| 9 | Тесты и CI | Публичные тесты, детерминизм, стресс и shutdown |
| 10 | Spike по free-threading | Ответ по GIL с цифрами, без внедрения по умолчанию |

## Критерии готовности этапов 0–2

- baseline зафиксирован в `docs/reports/baseline.md`;
- дубли `VisualCache`/`IdCache` сведены в `caches.py`;
- комментарии и докстринги переведены на русский;
- 100 000 циклов create/remove не увеличивают число занятых слотов;
- stale-команды `remove`/`render` от старого поколения не применяются к
  переиспользованному `render_id`;
- юнит-тесты и стресс-тесты проходят.

## Этап 2: lifecycle и ID

Что изменено:

- `Stream` выдаёт `render_id` из free-list `deque` и хранит поколение каждого
  слота в `_render_generations`;
- ответ регистрации содержит `object_id`, `render_id` и `generation`;
- `GameObject` хранит `_generation`, передаёт его в `remove`/`render` и
  публикует в `script_data`/`component_data`;
- повторный `register()` идемпотентен только для живого поколения; после
  удаления объект регистрируется заново;
- `Stream.__remove` освобождает слот только после удаления записи, а
  `__render`/`__remove` игнорируют команды чужого поколения;
- `find_object` переносит `_generation` в найденный объект;
- `validate_object_data` запрещает пользовательские `_id`, `object_id`,
  `render_id`, `_object_id`, `_render_id`, `_generation`.

Остаточная гонка: скрипт, который уже находится внутри `update()` в момент
удаления объекта, теоретически может успеть записать в общий visual cache до
следующей проверки живости. Этап 3 сужает её: поколение проверяется на каждом
шаге, поэтому после удаления скрипт не делает новых записей; окно остаётся
только для уже начатого `update()`.

## Этап 3: один sim-процесс и кооперативный планировщик

Что изменено:

- `script.__init__` больше не запускает бесконечный цикл и не создаёт поток:
  конструктор готовит зависимости и один раз вызывает `start()` через
  `__activate()`;
- добавлен `script.step()` — одна итерация опроса часов, ввода, `update()` и
  догоняющих `fixed_update()`; возвращает `False`, когда объект удалён,
  слот переиспользован или скрипт остановлен;
- `script.run_forever()` сохранён для автономного запуска без планировщика, а
  `script.shutdown()` гарантирует один вызов `stop()` и освобождение кэшей;
- зависимости `push_dependencies`/`pop_dependencies` выставляются вокруг
  `start()` и каждого шага, поэтому contextvar не смешивает скрипты;
- `scripter_runner` стал кооперативным планировщиком: один процесс, один поток,
  общий список экземпляров и последовательный вызов `step()`;
- ошибка одного скрипта останавливает только его, остальные продолжают шаг;
- удаление скрипта освобождает его статус в `proccess_status_info`, а
  `EOFError`/`BrokenPipeError`/`OSError` при завершении Manager считаются
  штатным выходом;
- `render.py` запускает `worker_count = 1`; очереди и статусы пока сохранены
  для совместимости `Stream`, их отказ — этап 4.

Гонка stale-записи сужена до одного уже начатого `update()`: шаги скриптов
последовательны, а после удаления объекта следующий шаг завершает цикл.

Проверки:

- `137` юнит-тестов, включая шаг скрипта, смену поколения, однократные
  `start()`/`stop()` и изоляцию ошибок в планировщике;
- полный стресс `python tests/stress_test.py --scenario all --workers 1`:
  `37/37`, `ALL_STRESS_OK`;
- `scripts.updates` — `93.48` updates/s при цели `100` (`93.48%`);
- `motion.updates_mean` — `99.48` updates/s, `motion.gap_max` — `30.46` мс;
- регистрация остаётся Manager-bound: p50 `2.961` мс, p95 `3.405` мс,
  p99 `3.718` мс — это цель этапа 4.

## Этап 4: отказ от Manager на пути команд

Что изменено:

- 4a: очереди команд переведены с Manager-прокси на обычные
  `multiprocessing.Queue`; `worker_ready` и `proccess_status_info` — на
  `multiprocessing.Array`, блокировки — на `multiprocessing.Lock`;
- 4b: реестр объектов стал локальным словарём внутри процесса `Stream`;
  другие процессы не читают его напрямую, а получают данные командами и
  снимками визуального кэша;
- `input_cache` вынесен в отдельный общий словарь: там остаются только
  события мыши и клавиатуры, которые читают скрипты;
- Manager-индексы идентичности, повышение bucket до `manager.list` и
  layer-индексы удалены; поиск по `layer` сканирует локальный реестр и
  читает `visual_cache`;
- команды чтения реестра (`find_object`, `camera_targets`, `clear`, `stats`)
  выполняет `Stream`; ответы идут через `main_out_stream`, для консоли — через
  отдельный `console_out_stream`;
- `script.find_object` и `_Camera` в production ходят в `Stream` по флагу
  `find_object_via_stream`; локальный fallback сохранён для тестов;
- живость скрипта и повторная регистрация проверяются по
  `IdCache.get(render_id, "generation")`; общий `object_generation` остался
  дешёвым триггером проверки;
- `Stream.__remove` сбрасывает поколение и `id` слота, поэтому stale-скрипт
  не может работать с переиспользованным `render_id`;
- рендерер получает `object_id`, `identity`, `scripts` и `collider` прямо в
  команде `add`; общий `object_cache` из `render.Game` удалён;
- консольные `clear` и `show` используют команды `clear`/`stats`, локальный
  путь сохранён для встраиваний без процесса `Stream`.

Проверки:

- `144` юнит-теста, включая команды Stream, поколения слотов, клиентские
  `find_object`/`camera_targets`, оверлей и консольный `clear`;
- полный стресс `python tests/stress_test.py --scenario all --workers 1`:
  `38/38`, `ALL_STRESS_OK`, отчёт `docs/reports/stage4_all.json`;
- регистрация: p50 `0.895` мс, p95 `1.059` мс, p99 `1.128` мс,
  `1100` объектов/с (было p99 `3.917` мс после 4a);
- `scripts.updates` — `93.95` updates/s, `motion.updates_mean` — `99.96`
  updates/s;
- цель p99 `< 1` мс почти достигнута: остаток — запрос и ответ через
  `multiprocessing.Queue` на каждый объект. Следующий шаг для строгого
  `< 1` мс — кольцевой буфер команд в shared memory, а не дальнейшая чистка
  словаря.

## Этап 5: снимок состояния, представления полей и планировщик по дедлайну

Что изменено:

- `scripter_runner.__run_once()` один раз за проход читает поля
  `ENGINE_STATE_LOOP_FIELDS` и передаёт всем скриптам один снимок состояния;
  `script.step(state=None)` сохранён для тестов и автономного цикла;
- планировщик держит период по дедлайну (`next_deadline += period`), а не
  «работа + `sleep`»; задолженность после долгого прохода не накапливается;
- в `memory_lib` добавлены `ObjectCache.buffer`, `field_view()` и
  `position_view()`; `FieldView.get_lockless()` читает число без блокировки,
  запись идёт под stripe-блокировкой;
- `Visual` использует заранее собранные представления полей и кэшированный
  признак изменения вместо повторного поиска по словарю; представления
  сбрасываются при `_apply_registration()`;
- объекты сцены регистрируются напрямую в локальном реестре `Stream`
  (`__register_scene_objects`), без команды `register_many` и ожидания ответа
  через `main_out_stream`; порядок публикации сохранён: сначала
  `_apply_registration()` для всех объектов, затем `_publish_registration()`;
- ответы `main_out_stream` маршрутизируются через общий stash по
  `request_id`: читатель, получивший чужой ответ, возвращает его в
  `objects_cache`, а ожидающий забирает оттуда. Это устранило потерю ответов
  `stats`/`camera_targets`/`register_many` при нескольких читателях.

Масштабирование сценария `scripts` (цель `100` updates/s):

| Скриптов | До этапа 5 | После этапа 5 |
|---:|---:|---:|
| 1 | 93.97 | — |
| 10 | 92.99 | — |
| 100 | 77.97 | — |
| 500 | 44.95 | 100.04 |
| 1000 (100 итераций) | — | 59.82 |
| 1000 (лёгкие) | — | 99.92 |
| 2000 (лёгкие) | — | 49.69 |

До этапа 5 время прохода росло с числом скриптов: каждый скрипт отдельно
читал состояние движка и искал поля визуального кэша. После этапа 5 проход
тратит время на сами шаги: 500 скриптов держат цель, 1000 тяжёлых скриптов
упираются в стоимость пользовательского `update()`, а 1000–2000 лёгких — в
стоимость каждого шага: пустой `step()` и одну запись визуального поля.

Микрозамеры без процессов (кэш на 2000 сегментов):

- пустой `step(snapshot)` — около `1.7` мкс;
- `ObjectCache.get_many_lockless` — около `1.7` мкс;
- `FieldView.get_lockless` — около `0.7` мкс;
- `FieldView.set` — около `4.7` мкс, из них `2.2` мкс приходится на
  `multiprocessing.Lock`;
- `ObjectCache.set` напрямую — около `3.5` мкс.

Проверки:

- `148` юнит-тестов, включая прямую регистрацию сцены и маршрутизацию чужих
  ответов через stash;
- полный стресс `python tests/stress_test.py --scenario all --workers 1`:
  `38/38`, `ALL_STRESS_OK`, отчёт `docs/reports/stage5_all.json`;
- старт сцены после прямой регистрации — около `0.64` с вместо десятков
  секунд при потере ответа;
- регистрация объекта: p95 `1.130` мс, p99 `1.349` мс; пакетная —
  `7086.7` объектов/с;
- `scripts.updates` — `99.99` updates/s, `motion.updates_mean` — `99.48`
  updates/s.

Дальнейший резерв — не батчинг dirty-флагов, а снижение стоимости записи и
шага. Замеры показывают, что при 2000 лёгких скриптах проход упирается в
`rotation += 1`: около `11.2` мкс на шаг против `1.7` мкс у пустого
`update()`. В записи `FieldView.set` около `4.7` мкс, из них `2.2` мкс —
`multiprocessing.Lock`. Батчинг помогает только нескольким записям в одном
`update()`, а типичный скрипт делает одну запись, поэтому выигрыша не даст.
Следующий серьёзный шаг — версии/seqlock для числовых полей вместо
stripe-блокировки на каждую запись (этап 6). Он должен сохранить атомарность
позиции и видимости и требует отдельного набора стресс-проверок.

## Позиция по GIL

- GIL нельзя отключить в обычной сборке CPython; нужна free-threaded сборка
  `python3.14t` (PEP 703, PEP 779).
- Free-threading даёт примерно 5–10% просадки single-thread и требует
  потокобезопасности всех общих структур.
- OpenGL-контекст всё равно должен работать в одном потоке.
- Основной выигрыш даёт не free-threading, а один sim-поток с кооперативным
  планировщиком и, при необходимости, шардирование по объектам на процессы.
- Free-threaded spike выполняется только после этапов 1–9 и только если
  профиль показывает CPU-bound нагрузку в скриптах.
