# Arcade test engine

## Формат объекта

Каждый объект сцены — JSON-объект с обязательным `object_type`. Встроенные типы и компоненты объявлены централизованно в `scene.py` в таблице `OBJECT_TYPE_RULES`: для каждого типа там заданы `allowed` и `required`. Кастомные компоненты можно добавлять верхнеуровневыми ключами, как описано ниже. Чтобы изменить правила или добавить тип, достаточно поправить эту таблицу.

| `object_type` | Допустимые компоненты | Обязательные компоненты |
| --- | --- | --- |
| `static_object` | `id`, `visual`, `transform` + кастомные | `id` |
| `dynamic_object` | `id`, `visual`, `scripting`, `transform` + кастомные | нет |
| `background_object` | `visual`, `transform` + кастомные | `visual` |
| `camera` | `id`, `visual`, `transform` + кастомные | `id`, `visual` |
| `manager` | `id`, `scripting` + кастомные | `id`, `scripting` |

Любой другой верхнеуровневый ключ считается кастомным компонентом. Имя ключа должно совпадать с именем класса и файла в `access/components`, а значение — содержать свойства компонента напрямую:

```json
"rotate_on_click": {
  "degrees": 90
}
```

Обёртки `path` и `properties` для такого компонента не нужны. Старый массив `components` с `path`/`properties` продолжает поддерживаться для совместимости.

`id.type`, если он указан, должен совпадать с `object_type`. Identity хранится в `IdCache`, визуальные данные — в `VisualCache`; они не дублируются в `objects_cache`. В нём остаются служебные данные и конфигурация скриптов.

Пример цели камеры:

```json
{
  "object_type": "camera",
  "id": {"name": "alpha", "class": "CameraTarget", "type": "camera"},
  "visual": {
    "sprite": "access/resources/img.png",
    "position": [0, 0], "scale": 0.2, "rotation": 0, "alpha": 1
  }
}
```

`scene.validate_object_data` проверяет тип, неизвестные и лишние компоненты, обязательные поля, конечность чисел и длину строк для общих кэшей до регистрации объекта. Ошибка возвращается вызывающему коду как `ValueError` с объяснением.

## Пути к ресурсам и скриптам

Относительные пути в сценах — `visual.sprite`, `scripting.scripts` и `components[].path` — разрешаются относительно каталога проекта (рядом с `config.py`), а не текущего рабочего каталога. Абсолютные пути также поддерживаются. Кастомный компонент из верхнеуровневого ключа автоматически ищется в `access/components` по имени ключа. Благодаря этому движок можно запускать из любого каталога, не меняя сцены и скрипты.

Если текстура не загрузилась, рендерер печатает ошибку и использует заметную розовую заглушку вместо падения. Неудачный путь запоминается, поэтому повторных попыток загрузки и повторных сообщений в журнале не будет; остальные объекты продолжают отрисовываться.

Если изображение объекту не нужно, укажите в `visual.sprite` строку `"None"`. Объект останется в сцене: позиция, `transform`/коллизии, скрипты и слежение камеры продолжат работать, но спрайт не будет виден. Это именно строка `"None"`, а не JSON `null`.

## Создание объекта из JSON

В скрипте доступен короткий API:

```python
from pyengine import create_object, creat_object

new_object = self.create_object("""
{
  "object_type": "background_object",
  "visual": {
    "sprite": "access/resources/img.png",
    "position": [10, 20], "scale": 1, "rotation": 0, "alpha": 1
  }
}
""")
```

`create_object` (и совместимый алиас `creat_object`) принимает JSON-строку, готовый `dict` или список объектов. Метод возвращает зарегистрированный `GameObject`; для списка — список объектов. `register()` отправляет команды регистрации и скриптов, связывает объект с общими кэшами и автоматически вызывает `render()`, если у объекта есть `Visual` — независимо от наличия `scripting`.

## Типы объектов

- `static_object` — объект с Identity; скриптинг запрещён.
- `dynamic_object` — произвольное сочетание Identity, Visual и Scripting.
- `background_object` — объект только с Visual.
- `camera` — именованная визуальная цель, за которой может следить камера.
- `manager` — объект Identity и Scripting для системного поведения.

## Функции скриптов

- `is_pressed(button)` проверяет, удерживается ли клавиша.
- `find_object(by, value)` возвращает первый объект, совпавший по атрибуту. `by`: `c`/`class`, `n`/`name`, `l`/`layer`, `t`/`type`. Возвращаемый объект — прокси: Visual читает и записывает `VisualCache`.
- `create_object(json_text)` / `creat_object(json_text)` создаёт и регистрирует объект из JSON-строки, `dict` или списка.
- `stop()` вызывается один раз, когда объект скрипта удалён из сцены или цикл скрипта завершился. Переопределите его для освобождения своих ресурсов.

## Камера

При старте контроллер выбирает объект типа `camera` с первым именем в алфавитном порядке (без учёта регистра). Камера постоянно следует за его координатами.

Скрипт контроллера изменяет позицию выбранного объекта через `Camera.move_camera` / `Camera.moveto_camera`; изменения записываются в `VisualCache` вместе с общим тиком. Рендерер только считывает координаты и ID цели из общего состояния камеры; очередь для движения и переключения камеры не используется.

- `Camera.move_camera(dx, dy)` или `Camera.move_camera([dx, dy])` сдвигает выбранную цель.
- `Camera.moveto_camera(x, y)` задаёт координаты цели.
- `Camera.switch(name)` переключает слежение на цель типа `camera` с точным именем; возвращает `True`, если цель найдена.
- `Camera.swich(name)` оставлен как совместимый алиас с написанием из раннего API.
- `Camera.scale_camera(scale)` меняет масштаб отображения.

В примере `access/scripts/camera.py` клавиши WASD двигают выбранный объект, `1` и `2` переключают цели `alpha` и `beta`.

## Тик симуляции и интерполяция

Симуляция идёт фиксированными шагами `FIXED_DT = 1 / SIMULATION_HZ` (по умолчанию 100 Гц). Поток `tact_counter` публикует в общем кэше не только `GlobalTime`, но и номер тика `Tick`. Все скрипты читают этот же номер и выполняют `fixed_update()` для каждого пропущенного тика по порядку, поэтому один и тот же тик означает одно и то же состояние для всех процессов.

Когда скрипт присваивает `GameObject.Visual.position`, позиция записывается в `VisualCache` вместе с номером тика. Скрипты, которые не меняют позицию, всё равно публикуют «сердцебиение» с текущим тиком. Благодаря этому рендерер видит снапшот каждого живого скриптового объекта на каждом фиксированном тике.

Рендер выбирает один общий `render_tick` для всех спрайтов, камеры и отладочных оверлеев:

- обычное значение — текущий тик минус `POSITION_INTERPOLATION_DELAY`;
- если живой скрипт отстал, тик ограничивается самым старым опубликованным тиком, чтобы не читать данные впереди отстающего скрипта;
- скрипт, не публиковавший тик дольше `SNAPSHOT_ACTIVE_WINDOW`, считается остановленным и больше не задерживает рендер.

В ожидании участвуют только объекты со своим скриптовым циклом, которые публикуют heartbeat на каждом тике. Объекты без скрипта — например, цель камеры, которая перестала двигаться, — не удерживают общий тик: иначе после остановки камеры весь кадр замирал бы до истечения окна активности, а затем резко прыгал вперёд.

Поскольку объект и цель камеры интерполируются по одному и тому же номеру тика, их относительное экранное смещение остаётся постоянным при движении в одном направлении. `POSITION_INTERPOLATION_DELAY` — это только страховочное окно задержки, а не средство борьбы с рассинхронизацией; увеличивать его вместо исправления причин дрожания не нужно.

Все константы находятся в `config.py`: `SIMULATION_HZ`, `FIXED_DT`, `POSITION_INTERPOLATION_DELAY`, `POSITION_HISTORY_SIZE`, `SNAPSHOT_ACTIVE_WINDOW`.
