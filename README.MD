# pyengine

<p align="center">
  <b>Лёгкий 2D-движок на Python и Arcade с авторитетным мультиплеером</b><br>
  Фиксированный тик · мультипроцессная симуляция · server authority · предсказание движения
</p>

**pyengine** — компактный игровой движок для 2D: сцены описываются JSON,
поведение — обычными Python-скриптами и переиспользуемыми компонентами.
Симуляция идёт фиксированными шагами 100 Гц, рендер интерполирует состояние
между тиками, а мультиплеер построен по модели **server authority**: сервер
владеет миром, клиент присылает только ввод и предсказывает своего игрока.

Движок не требует тяжёлых фреймворков: для сети используется только
стандартная библиотека Python. Одиночная игра, выделенный сервер и клиент —
это один и тот же код симуляции в разных ролях.

## Возможности

- **Данные вместо кода.** Сцена — JSON-массив объектов; правила типов
  собраны в одной таблице `OBJECT_TYPE_RULES` в `scene.py`.
- **Фиксированный тик.** Симуляция идёт с `SIMULATION_HZ = 100`, все процессы
  видят один и тот же номер тика.
- **Плавный рендер.** Позиции интерполируются по истории тиков; для сетевых
  объектов добавляется общая задержка и ограниченная экстраполяция.
- **Server authority.** Сервер выполняет скрипты и валидирует клиентов;
  клиент не может диктовать позиции объектов.
- **Предсказание и коррекции.** Клиент предсказывает только собственный
  объект, а расхождения плавно принимает через `CORRECTION`.
- **Роли скриптов.** `scripting.network` задаёт оси `authority`,
  `replication`, `prediction`, `input`: что симулирует сервер, что
  реплицируется и что предсказывает владелец.
- **Компоненты.** Поведение можно подключать к любому объекту сцены
  верхнеуровневым ключом, без правки самого объекта.
- **Триггер-зоны.** `trigger_object` задаёт выпуклый полигон и фильтр
  `activates`; сервер присылает скриптам `on_trigger_enter`/`on_trigger_exit`.
- **Наблюдаемость.** Консольные команды `show`, `pshow`, `vshow`, `ishow`,
  `overlay`, `clear`; отдельный стресс-тест для горячего пути.
- **Только stdlib для сети.** `socket`, `selectors`, `struct`, `threading`,
  `multiprocessing`, `queue`, `json`, `zlib`, `time` — без ENet и Twisted.

## Быстрый старт

### Требования

- Python 3.10+ (проверено на 3.13);
- Arcade 3.x и Pyglet 2.x — ставятся из `requirements.txt`;
- для клиента нужен OpenGL-контекст, сервер работает headless.

### Установка

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

### Одиночная игра

```powershell
python render.py
```

По умолчанию запускается `access/scenes/scene1.json` в режиме `solo`.
Другую сцену можно указать явно:

```powershell
python render.py --scene access/scenes/net_demo.json
```

### Мультиплеер

Самый быстрый способ — режим `host`: клиент сам поднимает сервер, ждёт
готовности и подключается к нему.

```powershell
python render.py --mode host --port 7777 --name host
```

Выделенный сервер и отдельные клиенты:

```powershell
# сервер
python server_main.py --host 0.0.0.0 --port 7777 --max-players 8 --anticheat log --no-console

# клиенты
python client_main.py --host 192.168.1.10 --port 7777 --name player
```

Полезные параметры клиента: `--scene`, `--token`, `--anticheat log|kick`.
Сцену также можно задать переменной окружения `PYENGINE_SCENE`.

### Управление в демо-сцене

| Клавиши | Действие |
| --- | --- |
| `W`, `A`, `S`, `D` | Двигать цель камеры |
| `Q`, `E` | Отдалить / приблизить камеру |
| `1`, `2` | Переключить цель камеры (`alpha` / `beta`) |
| клик по объекту | Повернуть `tilt_trigger` и создать новых участников |

## Как устроен движок

```text
┌──────────────── клиент (Arcade) ────────────────┐      TCP       ┌──────────── сервер (headless) ────────────┐
│                                                 │                │                                            │
│  Game: ввод, отрисовка, интерполяция            │ ◀────────────▶ │  GameServer: accept, снапшоты, валидация   │
│  NetClient.pump() в on_update                   │                │  Stream: реестр объектов, тик, VisualCache │
│  Stream: локальные скрипты + предсказание       │                │  scripter_runner: скрипты, 100 Гц          │
│                                                 │                │                                            │
└─────────────────────────────────────────────────┘                └────────────────────────────────────────────┘
```

Ключевые принципы:

1. **Один источник истины.** Серверный тик и серверное состояние — эталон.
   Клиент присылает ввод и «заявку» на проверку предсказания, но не позиции.
2. **Клиент не симулирует чужое.** Удалённые реплицируемые объекты приходят
   снапшотами; клиент только интерполирует их между тиками.
3. **Клиент предсказывает только своего.** `prediction=owner`-скрипты
   запускаются лишь для объекта с совпавшим `owner_render_id`.
4. **Скрипты фильтруются по роли.** Сервер запускает объекты с
   `authority=server`, клиент — локальные скрипты и своё предсказание.
5. **Расхождения сглаживаются.** `CORRECTION` не телепортирует объект, а
   плавно принимается рендером.

Подробности — в [NETWORK_ARCHITECTURE.md](NETWORK_ARCHITECTURE.md).

## Справочник

### Формат объекта

Каждый объект сцены — JSON-объект с обязательным `object_type`. Встроенные
типы и компоненты объявлены централизованно в `scene.py` в таблице
`OBJECT_TYPE_RULES`: для каждого типа там заданы `allowed` и `required`.
Кастомные компоненты добавляются верхнеуровневыми ключами. Чтобы изменить
правила или добавить тип, достаточно поправить эту таблицу.

| `object_type` | Допустимые компоненты | Обязательные компоненты |
| --- | --- | --- |
| `static_object` | `id`, `visual`, `transform` + кастомные | `id` |
| `dynamic_object` | `id`, `visual`, `scripting`, `transform` + кастомные | нет |
| `background_object` | `visual`, `transform` + кастомные | `visual` |
| `camera` | `id`, `visual`, `transform` + кастомные | `id`, `visual` |
| `manager` | `id`, `scripting` + кастомные | `id`, `scripting` |

Любой другой верхнеуровневый ключ считается кастомным компонентом. Имя ключа
должно совпадать с именем класса и файла в `access/components`, а значение —
содержать свойства компонента напрямую:

```json
"rotate_on_click": {
  "degrees": 90
}
```

Обёртки `path` и `properties` для такого компонента не нужны. Старый массив
`components` с `path`/`properties` продолжает поддерживаться для
совместимости.

`id.type`, если он указан, должен совпадать с `object_type`. Identity
хранится в `IdCache`, визуальные данные — в `VisualCache`; они не
дублируются в `objects_cache`. В нём остаются служебные данные и
конфигурация скриптов.

Пример цели камеры:

```json
{
  "object_type": "camera",
  "id": {"name": "alpha", "class": "CameraTarget", "type": "camera"},
  "visual": {
    "sprite": "access/resources/img.png",
    "position": [0, 0], "scale": 0.2, "rotation": 0, "alpha": 1
  }
}
```

`scene.validate_object_data` проверяет тип, неизвестные и лишние компоненты,
обязательные поля, конечность чисел и длину строк для общих кэшей до
регистрации объекта. Ошибка возвращается вызывающему коду как `ValueError`
с объяснением.

### Пути к ресурсам и скриптам

Относительные пути в сценах — `visual.sprite`, `scripting.scripts` и
`components[].path` — разрешаются относительно каталога проекта (рядом с
`config.py`), а не текущего рабочего каталога. Абсолютные пути также
поддерживаются. Кастомный компонент из верхнеуровневого ключа автоматически
ищется в `access/components` по имени ключа. Благодаря этому движок можно
запускать из любого каталога, не меняя сцены и скрипты.

Если текстура не загрузилась, рендерер печатает ошибку и использует заметную
розовую заглушку вместо падения. Неудачный путь запоминается, поэтому
повторных попыток загрузки и повторных сообщений в журнале не будет;
остальные объекты продолжают отрисовываться.

Если изображение объекту не нужно, укажите в `visual.sprite` строку
`"None"`. Объект останется в сцене: позиция, `transform`/коллизии, скрипты и
слежение камеры продолжат работать, но спрайт не будет виден. Это именно
строка `"None"`, а не JSON `null`.

### Создание объекта из JSON

В скрипте доступен короткий API:

```python
from pyengine import create_object, creat_object

new_object = self.create_object("""
{
  "object_type": "background_object",
  "visual": {
    "sprite": "access/resources/img.png",
    "position": [10, 20], "scale": 1, "rotation": 0, "alpha": 1
  }
}
""")
```

`create_object` (и совместимый алиас `creat_object`) принимает JSON-строку,
готовый `dict` или список объектов. Метод возвращает зарегистрированный
`GameObject`; для списка — список объектов. `register()` отправляет команды
регистрации и скриптов, связывает объект с общими кэшами и автоматически
вызывает `render()`, если у объекта есть `Visual` — независимо от наличия
`scripting`.

### Типы объектов

- `static_object` — объект с Identity; скриптинг запрещён.
- `dynamic_object` — произвольное сочетание Identity, Visual и Scripting.
- `background_object` — объект только с Visual.
- `camera` — именованная визуальная цель, за которой может следить камера.
- `manager` — объект Identity и Scripting для системного поведения.

### Функции скриптов

- `is_pressed(button)` проверяет, удерживается ли клавиша.
- `find_object(by, value)` возвращает первый объект, совпавший по атрибуту.
  `by`: `c`/`class`, `n`/`name`, `l`/`layer`, `t`/`type`. Возвращаемый
  объект — прокси: Visual читает и записывает `VisualCache`.
- `create_object(json_text)` / `creat_object(json_text)` создаёт и
  регистрирует объект из JSON-строки, `dict` или списка.
- `stop()` вызывается один раз, когда объект скрипта удалён из сцены или
  цикл скрипта завершился. Переопределите его для освобождения ресурсов.

Полный список методов — в [SCRIPTING_API.md](SCRIPTING_API.md).

### Камера

При старте контроллер выбирает объект типа `camera` с первым именем в
алфавитном порядке (без учёта регистра). Камера постоянно следует за его
координатами.

Скрипт контроллера изменяет позицию выбранного объекта через
`Camera.move_camera` / `Camera.moveto_camera`; изменения записываются в
`VisualCache` вместе с общим тиком. Рендерер только считывает координаты и ID
цели из общего состояния камеры; очередь для движения и переключения камеры
не используется.

- `Camera.move_camera(dx, dy)` или `Camera.move_camera([dx, dy])` сдвигает
  выбранную цель.
- `Camera.moveto_camera(x, y)` задаёт координаты цели.
- `Camera.switch(name)` переключает слежение на цель типа `camera` с точным
  именем; возвращает `True`, если цель найдена.
- `Camera.swich(name)` оставлен как совместимый алиас с написанием из
  раннего API.
- `Camera.scale_camera(scale)` меняет масштаб отображения.

В примере `access/scripts/camera.py` клавиши WASD двигают выбранный объект,
`Q` и `E` плавно отдаляют и приближают камеру, `1` и `2` переключают цели
`alpha` и `beta`.

### Тик симуляции и интерполяция

Симуляция идёт фиксированными шагами `FIXED_DT = 1 / SIMULATION_HZ`
(по умолчанию 100 Гц). Поток `tact_counter` публикует в общем кэше не только
`GlobalTime`, но и номер тика `Tick`. Все скрипты читают этот же номер и
выполняют `fixed_update()` для каждого пропущенного тика по порядку, поэтому
один и тот же тик означает одно и то же состояние для всех процессов.

Когда скрипт присваивает `GameObject.Visual.position`, позиция записывается в
`VisualCache` вместе с номером тика. Скрипты, которые не меняют позицию, всё
равно публикуют «сердцебиение» с текущим тиком. Благодаря этому рендерер
видит снапшот каждого живого скриптового объекта на каждом фиксированном
тике.

Рендер выбирает один общий `render_tick` для всех спрайтов, камеры и
отладочных оверлеев:

- обычное значение — текущий тик минус `POSITION_INTERPOLATION_DELAY`;
- если объект ещё не опубликовал данные до этого тика, для него используется
  последний доступный снимок; остальные объекты продолжают двигаться;
- один отстающий скрипт больше не замораживает весь кадр: он удерживает
  только свои объекты, а не общий тик.

Поскольку объект и цель камеры интерполируются по одному и тому же номеру
тика, их относительное экранное смещение остаётся постоянным при движении в
одном направлении. `POSITION_INTERPOLATION_DELAY` — это только страховочное
окно задержки, а не средство борьбы с рассинхронизацией; увеличивать его
вместо исправления причин дрожания не нужно.

Для удалённых сетевых объектов используется отдельная, более длинная задержка
`INTERP_DELAY_TICKS` (10 тиков ≈ 100 мс при 20 Гц снапшотов) и ограниченная
экстраполяция не дальше одного интервала снапшотов. Локальные объекты и
предсказание владельца остаются на короткой задержке
`POSITION_INTERPOLATION_DELAY` (40 мс).

Все константы находятся в `config.py` и `net/config.py`:
`SIMULATION_HZ`, `FIXED_DT`, `POSITION_INTERPOLATION_DELAY`,
`POSITION_HISTORY_SIZE`, `SNAPSHOT_ACTIVE_WINDOW`,
`OBJECT_LIVENESS_PERIOD`, `INTERP_DELAY_TICKS`.

### Консольные команды

В окне движка доступны служебные команды `show`, `pshow`, `vshow`, `ishow`,
`overlay` и `clear`.

`clear` удаляет из сцены все объекты, подходящие под указанный признак:

```text
clear <class|layer|name|type> <value>
```

| Признак | Сокращение | Что сравнивается |
| --- | --- | --- |
| `class` | `c` | `id.class` объекта. |
| `name` | `n` | `id.name` объекта. |
| `layer` | `l` | Текущее значение `Visual.layer`; значение слоя задаётся числом. |
| `type` | `t` | `id.type`, а если он не указан — `object_type`. |

Имена и классы сравниваются без учёта регистра команды (`CLEAR`/`clear`), но
значение признака — точно. Также принимаются русские названия: `класс`,
`имя`, `уровень`, `тип`.

```text
clear class test
clear name runner
clear layer 1
clear t dynamic_object
```

Удаление идёт через обычную команду `remove`: объект исчезает из сцены, его
спрайт убирается из рендера, а связанный скрипт получает `stop()`.

### Стресс-тест

Для проверки производительности ядра под разными нагрузками есть отдельный
раннер `tests/stress_test.py`: кэши, многопроцессная конкуренция, коллизии,
интерполяция рендера, живая регистрация объектов, пакетное создание и
скриптовые циклы. Он не входит в обычный `unittest`-набор.
