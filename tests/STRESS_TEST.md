# Стресс-тест ядра

> Часть проекта **pyengine**. Обзор — в [../README.MD](../README.MD), архив
> отчётов — в [../docs/reports/](../docs/reports/).

`tests/stress_test.py` — отдельный раннер для проверки производительности ядра под разными нагрузками. Он не входит в обычный `unittest`-набор: имя файла не начинается с `test_`, поэтому `python -m unittest discover -s tests` его не запускает.

Раннер можно запускать из любого каталога: пути к проекту, сцене и компонентам разрешаются от `config.py`.

## Быстрый запуск

```powershell
python tests/stress_test.py
python tests/stress_test.py --scenario cache,contention --processes 8 --duration 3
python tests/stress_test.py --scenario all --objects 2000 --json stress-report.json
python tests/stress_test.py --list
```

В конце печатается таблица с метриками и проверками. Код возврата `0`, если все проверки прошли, и `1`, если хотя бы одна упала. Успешный прогон заканчивается строкой `ALL_STRESS_OK`.

## Сценарии

| Сценарий | Что измеряет |
| --- | --- |
| `cache` | Скорость `ObjectCache.set/get/set_many/get_many/get_changed_values` и `ValueCache.set+get` в одном процессе. |
| `contention` | Многопроцессную работу с общей памятью: отдельные сегменты против одного общего сегмента. Показывает цену блокировок и деградацию при конкуренции. |
| `collision` | `transform_polygon` и SAT-проверку `convex_polygons_overlap`, а также полный конвейер «2 трансформации + проверка». |
| `render` | Реальные `_record_position`, `_position_at_tick` и `_interpolate_sprite_positions` из `render.py` без открытия окна и без GPU. |
| `registration` | Живой `Stream`: последовательное создание объектов через `create_object`, пропускную способность и задержки p50/p95/p99. |
| `batch` | Один вызов `create_object(list)` через локальный loopback-поток: валидация, `GameObject`, запись в общие кэши и команды регистрации. |
| `scripts` | Живой `Stream` с компонентом `tests/fixtures/stress_component.py`: сколько обновлений в секунду выполняет скриптовый цикл и сколько записей в `VisualCache` он делает. |
| `motion` | Живой `Stream` с `--motion-objects` движущимися объектами (`tests/fixtures/motion_component.py`): частота «сердцебиения», паузы между обновлениями и плавность общего `render_tick`. Ловит ситуацию, когда один отстающий скрипт замораживает кадр. |

## Параметры

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `--scenario` | `all` | `all` или список через запятую: `cache,contention,collision,render,registration,batch,scripts,motion`. |
| `--duration` | `2.0` | Длительность сценариев `contention`, `scripts` и `motion`, секунды. |
| `--objects` | `1000` | Число объектов для `render`, `registration` и `batch`. |
| `--pairs` | `100000` | Число пар/операций для каждого бенчмарка коллизий. |
| `--frames` | `60` | Число кадров в сценарии `render`. |
| `--cache-ops` | `100000` | Число операций на каждый бенчмарк кэша. |
| `--processes` | `2..4` | Число процессов в `contention`. |
| `--workers` | `1..2` | Число скриптовых воркеров в живых сценариях. |
| `--scripts` | `1` | Число объектов с нагружаемым компонентом. |
| `--motion-objects` | `16` | Число движущихся объектов в сценарии `motion`. |
| `--iterations` | `100` | Арифметических итераций внутри одного `update()` компонента. |
| `--timeout` | `20` | Тайм-аут запуска `Stream`, секунды. |
| `--json` | — | Путь для JSON-отчёта с конфигурацией, метриками и проверками. |

## Как читать результаты

- `contention.distinct` и `contention.shared` — один и тот же объём работы, но во втором случае все процессы пишут в один сегмент. Разница показывает стоимость сегментной блокировки; на неё влияют число ядер и фоновая нагрузка.
- `registration` включает реальный обмен через `multiprocessing.Manager`, поэтому он ожидаемо медленнее локального `batch`.
- `scripts.updates` зависит от `--iterations`, разрешения таймера Windows и числа воркеров. Это не жёсткий лимит движка, а фактическая скорость цикла на данной машине. Рядом выводятся `scripts.target` (значение `SCRIPT_UPDATE_HZ` из `config.py`) и `scripts.efficiency` — процент от целевой частоты.
- `render` — это CPU-бенчмарк математики интерполяции. Он не измеряет GPU, загрузку текстур или `arcade`-окно. Основной прогон — худший случай: все объекты помечены движущимися. `render.interpolation.static_frame_p95` — отдельный прогон с пустым набором движущихся спрайтов; статическая сцена не должна тратить время на интерполяцию вовсе.
- `motion` показывает, что при большом числе движущихся объектов общий `render_tick` не замирает и не прыгает. `motion.render_frozen` — доля кадров без сдвига тика, `motion.render_max_step` — максимальный скачок в тиках; при исправном движке скачок не превышает 3 тиков. `motion.gap_p95` — пауза между «сердцебиениями» объектов; она должна укладываться в `POSITION_INTERPOLATION_DELAY`.
- «Сердцебиение» (heartbeat) в `motion` публикуется из `fixed_update()`, поэтому его частота ограничена `SIMULATION_HZ` (100 Гц), а не `SCRIPT_UPDATE_HZ`. Проверки сценария сравнивают `motion.updates_*` именно с `SIMULATION_HZ`; низкая частота «сердцебиения» при высокой `SCRIPT_UPDATE_HZ` — ожидаемое поведение, а не деградация скриптового цикла.
- Проверки внутри сценариев (`checks`) подтверждают, что замеры не являются фиктивными: кэши возвращают записанные значения, маска изменений (dirty-mask) очищается, коллизии находят и пересечение, и зазор, объекты действительно появляются в кэшах, а компонент реально меняет `rotation`.

## Живые сценарии и Windows

`registration`, `scripts` и `motion` запускают настоящий `Stream` и скриптовые процессы. На Windows используется `spawn`, поэтому в раннере сохранены защита `if __name__ == "__main__"` и функции воркеров верхнего уровня. Не запускайте эти сценарии через `python -c` или интерактивно — используйте файл `tests/stress_test.py`.

Если `Stream` не успел подняться, увеличьте `--timeout`. Для слабых машин можно уменьшить `--objects`, `--pairs`, `--cache-ops` и `--processes`.
